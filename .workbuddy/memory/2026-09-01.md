## 登录成功但显示「未登录」——profiles RLS 无限递归 42P17（前端兜底 commit `19a6976`）

### 现象
杨茹：登录有「登录成功」提示，但界面顶栏/侧边栏始终显示「未登录」，功能页也进不去。

### 真根因（数据库，不是前端）
用 anon key 直接查 REST 发现：
```
GET /rest/v1/profiles?select=id → HTTP 500
{"code":"42P17","message":"infinite recursion detected in policy for relation \"profiles\""}
```
而 `qc_shares` 同 key 查询是 200 → key 有效、网络正常 → 确认是 **profiles 表 RLS 策略无限递归**。

来源是之前 `add_member_invite_rls.sql`（杨茹已执行过）第 43–54 行的两条 profiles policy：
```sql
CREATE POLICY "管理员可查看所有成员" ON public.profiles FOR SELECT
  USING ( auth.uid() = id OR EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role='admin') );
CREATE POLICY "管理员可修改任意成员" ON public.profiles FOR UPDATE
  USING ( ... EXISTS (SELECT 1 FROM profiles ...) )
```
USING 子句里 `EXISTS(SELECT ... FROM profiles)` 引用了 profiles 自身。
查 profiles 时要评估这条 policy → policy 里又查 profiles → 再次触发本 policy → 死循环 42P17。
结果：任何查 profiles 的操作（登录后取用户信息、成员列表、依赖 profile 的全部功能）全 500。

### 时间线关联
- 8/30 杨茹执行 `add_member_invite_rls.sql` → 引入递归 policy → 此后登录必 500
- 但当时 `app.js` 还有 `profilesSub` 重复定义 bug（第三轮），app.js 整体解析失败，登录按钮根本没反应，没暴露「未登录」
- 修掉重复定义（011c0cc）后 app.js 恢复 → 登录按钮能用 → 但 profiles 查询 500 → 暴露「登录成功却未登录」

### 前端兜底（commit `19a6976`，已 push）
- `signIn()` 成功后**立即** `currentUser = data.user` + `updateAuthUI()`，不再只靠 SIGNED_IN 回调
- `SIGNED_IN` / `getSession` 两处 profile 查询改 `maybeSingle()` + `try/catch` 兜底：查不到/失败时以 staff 角色兜底，至少能进系统、不再卡「未登录」
- ⚠️ 注意：前端兜底只能保证「进得去」，若 profile 真查不到会变成 staff（看不到管理功能）。**根本修复是数据库 RLS**

### 数据库根本修复（需杨茹执行 `fix_profiles_rls_recursion.sql`）
- 删除递归的 SELECT policy「管理员可查看所有成员」（它本就多余，基础 `SELECT USING(true)` 已允许全员查）
- 新增 `SECURITY DEFINER` 函数 `is_admin()`（以 owner 身份查 profiles，不受 RLS 约束，不递归）
- 用 `is_admin()` 重写「管理员可修改任意成员」UPDATE policy 与 `pending_invites` 管理 policy
- 文件：`fix_profiles_rls_recursion.sql`（幂等，可重复跑）

### 验证
- 前端 6 段内联脚本语法 0 错；已 push `011c0cc..19a6976`
- 数据库修复需杨茹在 Supabase SQL Editor 跑完后再验证（跑完 `profiles` 查询应恢复 200）

### 🚨 铁律（下次写 RLS 必记）
**绝不能在 profiles 表的 policy 的 USING/CHECK 子句里直接 `SELECT ... FROM profiles`** —— 必触发 42P17 递归，直接搞挂整个登录与所有依赖 profile 的功能。
需要判断「当前用户是不是管理员」时，一律用 `SECURITY DEFINER` 函数（如 `is_admin()`）封装，或在建 policy 前先 `CREATE FUNCTION` 包一层。其他表的 policy 引用 profiles（如 announcements 的 `EXISTS(SELECT FROM profiles)`）没问题，因为那作用在别的表上、且 profiles 的 SELECT 是 `USING(true)` 不递归；只有 profiles 自身的 policy 引用 profiles 才致命。
