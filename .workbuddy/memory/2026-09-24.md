## 花色素材页「加载太慢」修复：jsDelivr 301 是元凶（commit bae1214）

### 需求
茹姐截图反馈花色素材页「加载太慢，我想秒开」。

### 根因（实测锁定，链条完整）
1. `toCdnUrl()`（index.html ~11934 行）把图片 URL 输出成 `cdn.jsdelivr.net/gh/yangru2026/kefu-workbench@main/...`。
2. **jsDelivr 对本仓库的图片会返回 301**，Location 指向 `raw.githubusercontent.com`。
3. **`raw.githubusercontent.com` 国内直连极慢**——实测 `curl` 12s 超时失败（http=000）。
4. 首屏 20 张卡片图**每张都要吃一次 301 + 超时** → 页面长时间空白/图片逐个慢慢冒出来。
   - 对比实测：同源 `yangru2026.github.io` 直连同一张图 **200 OK，0.34KB→34KB，0.47~1.68s**。
5. 次要因素：`sw.js` 只处理**同源**请求（`isSameOrigin`），跨域的 jsDelivr 图片**根本没进缓存**，等于 SW 对图片完全没起作用。
6. 非瓶颈项（已确认无需改）：数据层早有秒显缓存（`kefu_cache_pattern_assets`，先渲染缓存再后台刷新）；
   卡片已分页（`PATTERN_PAGE_SIZE=20`）、已 `loading="lazy"`、首屏 6 张已 `fetchpriority="high"`；
   缩略图已是 34KB webp（thumb 目录 357 个文件）。

### 改动
1. **index.html `toCdnUrl()`**：改为输出**同源** `https://yangru2026.github.io/kefu-workbench/...`
   - 相对路径 → 同源绝对地址
   - 历史 jsDelivr 仓库地址 → 还原成同源（兼容 localStorage 旧缓存里可能存的旧值）
   - Supabase Storage / npm jsDelivr 地址 → 保持不动
   - 去掉原来 `url.includes('?')` 就原样返回的粗暴分支
2. **sw.js**：新增 `/images/` 图片缓存，策略 **stale-while-revalidate**（先返回缓存=秒开，同时后台静默拉新版）；
   - `IMG_CACHE = 'kefu-sw-img-v1'` **刻意不随 VERSION 变化**，SW 升级不会清掉用户已缓存的图
   - `IMG_MAX_ENTRIES = 800` 上限 + `trimCache()` 按插入顺序淘汰
   - `VERSION` v1 → v2（旧的 `kefu-sw-v1-*` 会被 activate 清理）
   - 注意 fetch 分支顺序：**isLib 必须排在 isImage 之前**（vendor 的 .js 不误判为图片）
3. `outputs/smoke-pattern-speed.js`：新冒烟脚本，mock 真实形态数据（thumb_*_url 用相对路径），
   断言 img src 无 jsdelivr、全部同源、**并用 `naturalWidth>0` 证明图片真实加载成功**。

### 验证
- `sw.js` node --check 通过；index.html 内联脚本 5 段 `new Function` 语法 0 错误。
- `toCdnUrl` 纯函数单测 6/6 通过（相对路径/已是同源/历史 jsDelivr/Supabase/npm 各自正确）。
- 无头冒烟：`imgCount=3`、`jsdelivrCount=0`、`sameOriginCount=3`、**`loadedOk=3`、`broken=0`**、无 pageerror、`swRegistered=true`。
- 推送 `b069e4b..bae1214` main。

### 教训
- **公共 CDN 不一定加速**：jsDelivr 的 gh 路径可能 301 到 `raw.githubusercontent.com`，
  该域名在国内基本不可用。给国内用户做 GitHub 托管资源，**同源 GitHub Pages 反而最稳**。
- **诊断顺序**：先 `curl -sI` 看状态码与 Location，再 `curl -sL -w '%{time_total}'` 看跟随重定向后的真实耗时——
  只看首跳状态码会漏掉"301 到坏域名"这种最坑的情况。
- **SW 只能缓存同源**：跨域图片进不了 SW 缓存，所以"把源改成同源"同时解决了可达性与可缓存性两件事。
- 部署后用户需 `Ctrl+Shift+R` 强刷一次（旧 index.html 在浏览器缓存里最多留 10 分钟）。

## 花色素材秒开（三）：价格页卡 → 29 款 Storage 花色预生成缩略图（commit f3307b2 + SQL 回填）

茹姐截图反馈「弥生价 / 极氧价这里卡」（价格速查页卡片图大半空白）。

### 根因
价格页与素材页共用卡片逻辑，其中 **28 款（弥生 25 款）花色的图仍是 Storage 原图**，
走 Supabase render 转换端点——该端点**服务端不缓存（CF BYPASS / no-cache）、每次实时转换、冷启动约 1.6s/张**，
价格页一次几十张卡片并发 → 这批明显卡住（截图里恰好第一张有图、其余空白 = 排队等待的典型形态）。

### 解法：预转换 + 存仓库 + 回填字段（内容 100% 来自原图，无错配风险）
1. `outputs/gen-storage-thumbs.js`：查出「thumb 字段为空且原图是 Storage URL」的记录，
   用 render 端点转 **400px q72 webp**，存 `images/patterns/thumb/u{记录id}_{eye|lens}.webp`
   （用 id 命名，不猜花色名，避免同名错配）。**41/41 张全部成功，平均 27KB**。
2. push 图片进仓库（f3307b2），GitHub Pages 构建后同源直连 200 OK。
3. `outputs/fix-storage-thumbs.sql` 回填 `thumb_eye_url`/`thumb_lens_url`（41 条 UPDATE）。
   ⚠️ **`pattern_assets.id` 是 UUID 类型**，SQL 里必须 `where id = '<uuid>'` 带引号，
   不带引号报 `42601 trailing junk after numeric literal`。

### 结果（复查分布）
- Storage 慢链路：**28 款 → 0 款**；同源 thumb 快链路：148 → **176 款**；无图 13 款（本来就没图）。
- 全站 189 款卡片主图现在**只有"同源缩略图"或"无图"两种状态**，不再有任何实时转换请求。
- 弥生 152 款：149 快 + 3 无图；极氧全部快链路。

### 经验沉淀

  会出现新的"慢链路"记录。复跑 `SBP_TOKEN=xxx node outputs/gen-storage-thumbs.js`
  → push → 跑生成的 SQL 三步即可再次清零。
- 价格页一次性渲染几十张卡片（按直径分组），比素材页分页 20 张更容易暴露慢图；

## 花色素材秒开（二）：41 条 Storage 原图改走图片转换端点（commit 15998c1）

修完 jsDelivr 后继续追查，发现**第二个、体量更大的根因**。

### 根因
- `pattern_assets` 有 **55 条**记录的 `thumb_eye_url`/`thumb_lens_url` 为空（不是之前估计的 41 条），
  它们的 `eye_img`/`lens_img` 形态分布：**41 个 Supabase Storage 完整 URL** / 25 个相对路径 / 44 个空。
- **那 41 张 Storage 图实测平均 1.24MB、最大 10.07MB（「D追光引力6片装」），41 张合计 50.88 MB**，
  21 张 > 800KB。这些卡片等于每次首屏都在从**新加坡**拉几 MB 大图 → 必卡。
- 对比：同源 `thumb/` 缩略图只有 34KB。
- 另：`thumb/` 目录有 357 个文件、数据库只引用了 293 个，孤儿 64 个；
  但**无法用 basename 自动补齐**（那 41 条的图片是 Storage UUID / 时间戳命名，与 thumb 目录文件名对不上）。
  → 结论：**别去猜文件名配对**（同名不同抛型会错配），直接在 URL 层解决。

### 解法：Supabase Storage 图片转换端点（零数据改动、立即生效）
URL 变形：`/storage/v1/object/public/` → `/storage/v1/render/image/public/`，后缀加
`?width=NNN&quality=NN&format=webp&resize=contain`

- 实测同一张 134KB 原图：`width=400&quality=72` → 51KB(jpeg)；`+format=webp` → 28.7KB；
  `&resize=contain` → 20KB；`width=360&quality=70&format=webp&resize=contain` → **9.25KB**。
- **最大的 10.07MB 图 → 25KB**（width=400&quality=72&format=webp）。

### 改动（index.html）
1. 新增 `toStorageRender(url, width, quality)`：Storage 原图 URL → 转换端点 + webp。
2. 新增 `toThumbUrl(url)`：卡片主图专用，Storage 图缩到 **400px / q72**；非 Storage 图原样返回
   （同源缩略图仍走 GitHub Pages）。
3. `toLargeImageUrl()` 加 Storage 分支：返回 **1200px / q80** webp，供 hover 与灯箱用
   （原实现对 Storage 返回 ''，导致 hover 直接拉 10MB 原图）。
4. 接入点：花色素材卡片主图 + hover（`renderPatterns`）、灯箱 `images[].thumb` 占位、
   价格速查卡片 `ppCardHtml`。`hd` 字段保留原图，仅作 large 失败时的兜底。
5. 参数选择理由：卡片显示约 200~300px 宽，400px 够 2x retina；灯箱才用 1200px。

### 验证
- 语法 0 错误；`toThumbUrl`/`toLargeImageUrl`/`toCdnUrl` 单测 6 组映射全部正确。
- 无头冒烟（mock 3 条：同源缩略图 ×2 + Storage 原图 ×1）：
  `imgCount=4`、`jsdelivrCount=0`、`storageRawCount=0`、`storageThumbCount=1`、
  **`loadedOk=4`（含 Storage 缩略图真实加载成功）、`broken=0`**、无 pageerror。
- 远端 blob sha / commit 与本地一致（`15998c1`）。

### 线上实测（outputs/bench-live-thumbs.js，无头浏览器加载 20 张真实线上缩略图）
- 第 1 次访问（冷缓存）：**20/20 全部成功**，总 8.5~14.8s（沙箱网络对 github.io 波动大；
  真实环境有 Fastly 边缘缓存会更快）
- 第 2 次访问（命中缓存）：**20/20，总耗时 1ms** ← 这就是「秒开」
- 对比旧方案：jsDelivr → 301 → raw.githubusercontent.com，国内 12s 超时、大量失败/破图。
- 结论：**首次能稳定出图、二次真正秒开**。若茹姐仍觉得首次慢，下一刀是给 GitHub Pages
  缩略图再瘦身（当前 34KB → 目标 15KB 以内），需重新生成 thumb 目录图片。

### ⚠️ 安全事件（本会话踩到）
- push 被拒：`push declined due to repository rule violations`，
  原因是 **GitHub Secret Scanning 检测到我把 Supabase token 硬编码进了两个诊断脚本**
  （`outputs/diag-storage-img-size.js`、`outputs/diag-thumb-gap.js`）。
- 处理：**不要点那个 unblock-secret 链接**；改脚本为 `process.env.SBP_TOKEN` 读取，
  再 `git commit --amend` 重写该 commit（未推送过，secret 未进远端），然后 push 成功。
- 顺手把本地 `outputs/exec-sql.js`、`outputs/check-aiq-policies.js` 也脱敏。
  **全仓 grep 确认无 `sbp_` 残留**。
- 教训：**任何要提交的脚本，token/key 一律走环境变量**。本项目的 `sbp_` token 是
  Supabase Personal Access Token（可管理整个项目，权限极高），绝不能进仓库。

### 补充：Supabase 图片转换端点的缓存行为
- 响应头 `Cache-Control: no-cache` + `CF-Cache-Status: BYPASS` → **Supabase 侧 CDN 不缓存**，
  每次请求都回源实时转换（冷启动首次约 1.6s，之后稳定 0.37~0.40s）。
- 因为是跨域，**我们的 Service Worker 缓存不到它**（SW 只处理同源）；
  实际靠浏览器自身的 ETag/304 缓存。
- 因此这套「同源 GitHub Pages 缩略图 + SW 缓存」是主要加速手段，
  Storage 转换端点只是把「几 MB」压到「几十 KB」的兜底。
