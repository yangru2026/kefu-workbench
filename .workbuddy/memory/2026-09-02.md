## 修复：图片全部加载失败的真根因——签名 URL 是相对路径（commit `4f33638` + `f385ab4`，已 push）

- **反馈**：修复 Supabase 初始化后，杨茹确认「原来是有图的」但表格/卡片里图片仍大量消失。
- **真根因（致命）**：`supabase.storage.createSignedUrl()` 在本项目本地 `lib/supabase.min.js` 版本里返回的是**相对路径** `/object/sign/qc-images/qc/...?token=...`（缺 `/storage/v1` 前缀、且非 `http` 开头）。原 `getImageUrl` 把这串**相对路径当有效 URL 直接返回并缓存**——浏览器解析成 `https://yangru2026.github.io/object/sign/...` 直接 404。更糟的是因为它非空（truthy），「签名失败回退公开 URL」的分支永远不触发，导致**全部图片都加载失败**。
- **验证手段**：直接 curl Supabase REST——`createSignedUrl` 返回相对路径；补成 `SUPABASE_URL + '/storage/v1' + 相对路径` 后 HTTP 200；仓库 `qc_records` 的 `scene_images` 字段存的是无扩展名 ID（如 `img_1787047553370_lfwghe`），存储桶文件为 `qc/img_...jpg`，路径拼接正确；`getPublicUrl` 公开地址验证 HTTP 200（bucket 实际是 public）。
- **修复**：`getImageUrl` 改为——① 签名 URL 若非 `http` 开头，补成 `SUPABASE_URL + '/storage/v1' + 相对路径`；② 仍拿不到有效 http 地址才回退 `getPublicUrl`；③ **只有 `http(s)` 开头的绝对地址才缓存并返回**，杜绝缓存坏的相对路径。公私 bucket 均通用。
- **缓存**：升级 `index.html` iframe 版本号到 `qc-v2.html?v=20260902g`。
- **验证**：inline script 语法 0 错；`4f33638..f385ab4` 已 push main。
- **排错要点（复用）**：qc-v2 图片不显示时，先用 `curl` 验证 `getPublicUrl` 公开地址 HTTP 状态；若签名 URL 是相对路径，必须补 `/storage/v1` 前缀才是绝对地址。

## 真根因：标记「已讲解/待讲解」会清空数据库图片链接（commit `6e07cc0`，已 push `f385ab4..6e07cc0`）
